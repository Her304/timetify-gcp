# Sign-up & Onboarding

- **Register** (`components/register/register.jsx`) = 2 steps: (1) basic info + consent checkboxes — `accepted_terms` **required** (gate; serializer rejects if not `True`), `marketing_opt_in` optional; (2) optional profile pic (reuses ≤1024 px / JPEG @ 0.7 compression). Submits one multipart `POST /api/register/`; `RegisterSerializer` accepts `profile_picture` + both flags. `registerUser` (`App.jsx`) then **auto-logs-in** via `/api/login/` and lands `/`.
- **Step-1 duplicate pre-check**: "next" (`goToStep2`) is async — after local validation it POSTs `{username,email}` to `POST /api/register/check/` (`RegistrationAvailabilityView`, `AllowAny`, `username__iexact`/`email__iexact`) and blocks step 2 if either is taken. **Advisory only** — `RegisterSerializer` still enforces uniqueness on final submit (fail-open: a network/5xx check error lets the user proceed). Duplicate messages go in `localErrors` so editing a field clears them and re-clicking "next" re-checks; a stale *server* error (bounced final submit) is hidden per-field via `dismissedServer`, reset on each new `errors` object.
- **Coach-mark tour** (`components/onboarding/OnboardingTour.jsx`): spotlight over real nav via `data-tour="schedule|feed|bell|profile|add"` anchors (present on both desktop header + mobile nav). Shows in `AppShell` when `currentUser.onboarding_completed === false` (not on `/chat`); last-step button reads "record my first class →" and finish → `/Add` (was `/feed`); persists via `PATCH /api/user/ {onboarding_completed:true}` (optimistic).
- **Material Symbols** webfont loaded in `index.html` (`add_reaction`, `frame_person` used on sign-up step 2).
- **Friend invites** (QR + link): profile → "invite friends" section shows a server-rendered QR (`GET /api/invite/qr/`, PNG, fetched as a blob) of `FRONTEND_URL/invite/<invite_code>`, a copyable link, native `navigator.share`, and a `mailto:`. `/invite/:code` route (`components/invite/inviteLanding.jsx`): logged-out → renders `<Register inviteInfo={{code,inviter}}>` (banner "@user invited you"; threads `invite_code` into the register POST → `RegisterSerializer.create` auto-friends both directions at `status=1`); logged-in → `POST /api/invite/<code>/accept/` friends them idempotently, then → `/feed`. Inviter banner data comes from `GET /api/invite/<code>/` (AllowAny, `PublicUserSerializer` + `university` added — the invite is an explicit share). Bad/expired codes never block sign-up.
- **Feed QR buttons** (`components/feed/QrModal.jsx`, wired via `PeopleSearch` `onShowQr`/`onScanQr`): two round buttons beside the "search ppl" bar. `qr_code` = show my QR + `@username`; `qr_code_scanner` = rear-camera scan (jsQR decodes frames off a hidden canvas → extracts the code from the `/invite/<code>` payload → **authenticated** `GET /api/invite/<code>/` so the response `status` reflects any existing relationship → profile card (pic, username, major, school, grad year)). Both `qr_code`/`qr_code_scanner` glyphs must stay in the Material Symbols `icon_names=` allowlist in `index.html`.
- **Two friend-add semantics — don't conflate them.** The four ways to add a friend split by whether the invitee is already registered:
  - *Both registered* (feed: manual username search **and** feed QR scan) = **send a friend request** (`Friend` row `status=0`); the invitee decides. QR scan calls `sendFriendRequest(inviter.id)` → `POST /api/friend-requests/` — the **same** consent path as the username "connect" button, **not** the accept endpoint. The `QrModal` card is status-aware: `status===1` → "already friends", `status===0` → "request pending", else a **send request** button. `sendFriendRequest` (`App.jsx`) returns `res.ok` so the modal can show sent-vs-error.
  - *Invitee unregistered* (invite QR / invite link → `/invite/<code>`) = **auto-friend both directions at `status=1`** with no request step, via `RegisterSerializer.create` (link sign-up) or `POST /api/invite/<code>/accept/` (`InviteAcceptView`, logged-in link open). The accept endpoint is reserved for that link flow — the feed scan must never call it, or it silently skips the request/consent period.
